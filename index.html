Introduction

  • What is Linked Art?
  • Why manuscripts need special treatment?

Presenter: Welcome everyone! Today we’ll dive into how Linked Art models manuscripts. We’ll cover the difference between the Work (the conceptual text) and the Object (the physical codex or scroll), and see concrete JSON-LD examples.

Core JSON-LD Structure

Every Linked Art document needs:

  • @context – Linked Art JSON-LD context URI
  • id – Unique HTTP(S) URI
  • type – CIDOC-CRM class or RDF class . (e.g., HumanMadeObject, LinguisticObject, Actor, Event)
  • _label – Human-readable label

Presenter: Quick refresher on the fundamentals: context, URI identity, RDF type, and the display label. This baseline applies to manuscripts just as much as paintings or digital items.

Core Classes for Manuscripts

Class Role
LinguisticObject The text content (Work)
HumanMadeObject The physical codex or scroll (Object)
DigitalObject Scanned or born-digital images/text
Dimension Measurements (leaves, folios, size)
Type Material categories (parchment, paper)

Reference: LinkedArt, Basic Patterns

Presenter: Here are the key classes. Note that the Work side is covered by LinguisticObject, while the Object side is HumanMadeObject. We’ll dive deeper next.

Manuscript Work vs. Manuscript Object

Aspect Manuscript Work Manuscript Object
Definition The intellectual text (author, title) The physical codex or scroll
Type Work (a subclass of PropositionalObject) HumanMadeObject
Key Properties title, creator, language, subject material, carrier, dimensions, binding
Relationships derived_from, translation_of material_used, physical_production

Presenter: Emphasize: the Work is conceptual; the Object is tangible. A single Work may have multiple Objects (e.g., two copies), and one Object carries exactly one Work.

Presenter This slide shows how you’d declare the Work. You see type: Work, the _label and properties like creator and language.

JSON-LD Example: Object

id: "https://data.example.org/object/001a"
type: HumanMadeObject
_label: "Codex Gigas (Prague Copy)"
carries:
  - type: LinguisticObject
    id: "https://data.example.org/work/001"
    _label: "Codex Gigas"
material:
  - _label: "Parchment"
dimension:
  - type: Dimension
    value: 636
    _label: "Leaves"
binding:
  - _label: "Wooden boards with leather"
currentOwner:
  - type: Group
    _label: "Prague National Library"

Presenter: Here’s the Object. Notice carries linking back to the Work, and the physical attributes (material, dimension, binding, currentOwner).

Which Properties Belong Where?

  • Work

    • Intellectual properties: title, language, subject, derived_from, translation_of

  • Object

    • Physical properties: material, dimension, binding, production, currentOwner

Presenter: Summarize: don’t mix up text-centric and object-centric properties. If you’re describing the content: it’s a Work. If you’re describing the codex: it’s an Object.

Structural Link: carries

The Object carries the Work:

carries:
  - type: LinguisticObject
    id: <Work URI>
    _label: <Work label>
  • Ensures clear separation and linkage.

Presenter: Remember: carries is the magic property that connects the physical container to the conceptual text. Always include it for manuscripts.

Recap & Best Practices

  • Model the intellectual text as Work (type: Work or LinguisticObject subclass).

  • Model the physical codex as Object (type: HumanMadeObject).

  • Link via carries.

  • Keep physical vs. conceptual properties distinct.

  • Use controlled vocabularies for materials, dimensions, binding types.

Presenter: Wrap up with these five take-aways. They’ll guide you whether you’re modeling a medieval codex or a modern artist’s book in Linked Art.
